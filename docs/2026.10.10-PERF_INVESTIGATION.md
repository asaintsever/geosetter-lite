# Performance & map display fixes

## Summary

This PR fixes three related issues:

1. **No markers displayed at all on folders with many photos** (page failed to load silently)
2. **Very long startup time** on directories with many photos (#38, "Running geosetter-lite is slow")
3. **Noticeable delay when selecting a photo** and **slow GPS updates** (#38)
4. **`gmake run ARGS="..."` broke on paths containing spaces** — the Makefile expanded `$(ARGS)` unquoted, so the shell word-split the path before `main.py` saw it. Now expanded as a single quoted argument (`$(if $(ARGS),"$(ARGS)")`, so bare `gmake run` still works).

All measurements below were taken on a folder of **241 geotagged JPEGs** (~7 MB each).

---

## Issue 1: No markers displayed on large folders

### Root cause

`MapWidget._generate_map_html()` embedded a **base64 thumbnail in every marker's popup**, and the whole page was passed to `QWebEngineView.setHtml()`. Qt WebEngine's `setHtml()` (without a base URL) has a size limit of ~**2 MB** (the content is routed through a data URL). Measured page sizes:

| Folder | Markers | Generated HTML |
|---|---|---|
| 3 photos (worked) | 3 | < 1 MB |
| 241 photos (broken) | 241 | **2.38 MB** → `setHtml` fails silently → blank map, no markers |

### Fix

Made popup content **lazy** in `geosetter_lite/ui/map_widget.py`:

- Removed the per-marker `_generate_popup_html()` call from the initial page — markers now only carry coordinates + filename.
- Added a `PopupProvider` QObject exposed over the WebChannel (`popupProvider`) with a `getPopupHtml(marker_id)` slot that generates the popup HTML (thumbnail included) on demand.
- Each marker shows the filename immediately and fetches the full popup via the channel on `popupopen`.

**Result:** initial HTML for 241 markers is **249 KB** (was 2.38 MB) — scales to thousands of photos.

## Issue 2: Long startup time

### Root cause

`FileScanner.scan_directory()` spawned **one exiftool process per file** — each spawn costs ~130 ms (Perl runtime init). 241 files → **~32 s** of blocked main thread before the window became usable.

### Fix

- New `ExifToolService.read_metadata_batch()`: one exiftool call per 50 files, chunks processed **in parallel** (4 worker threads), results mapped back to files via the `SourceFile` tag.
- `FileScanner.scan_directory()` uses the batched read. (The rare "auto-write Created Date" write-back stays per-file, only for files that actually need it.)

**Result:** directory scan went from **~32 s → ~3.5 s**; total app startup measured at **3.6 s**.

---

## Issue 3: Slow photo selection & slow GPS updates (#38)

### Root causes

**Selecting a photo:** `display_image()` re-encoded the **full-resolution** JPEG to PNG on every click (~0.5 s and a 24 MB temp buffer for a 12 MP file), kept a full-res `QPixmap` in memory, and smooth-scaled it on the main thread.

**Setting GPS:** after a GPS write, `reload_images()` re-scanned the **entire directory** (241 exiftool calls ≈ 30 s) even though only the modified files changed.

### Fix

- `display_image()` now downscales with PIL to ~2× the viewer size (HiDPI-aware) and builds the `QImage` directly from raw RGB bytes — no PNG round-trip, no full-resolution pixmap.
- `reload_images(changed_files=None)` gained a fast path: when the list of modified files is passed, only those files are re-read (one batched exiftool call), and the table/map are refreshed in place with the selection preserved. All metadata-edit call sites (GPS update, metadata editor, rotate, date/time shift, repair, set taken date, set GPS date) now pass their changed files.
- Drive-by bug fix: `ExifToolError` was caught in `main_window.py` but never imported (would have raised `NameError` on the first failure).

**Results:**

| Operation | Before | After |
|---|---|---|
| Click photo → displayed | ~0.5–1 s | **~128 ms** |
| GPS write → table/map refresh | ~30 s (full rescan) | **~245 ms** (targeted reload) |

## Leaflet memory audit

No unbounded leak found:

- Every `setHtml()` recreates the whole document — the map, tile cache and `window.imageMarkers` die with it. After the fixes, full page reloads only happen when the marker *set* actually changes (directory change, GPS write), **not per selection** — selection changes use a pure-JS icon swap (`_update_marker_icons`), which allocates nothing in the page.
- The old per-popup base64 thumbnails no longer exist in the page at all (see Issue 1).
- One churn issue fixed: reopening a popup re-encoded the same thumbnail every time. Added a `MapWidget._thumbnail_cache` (filepath → data URL), cleared in `clear_markers()` on directory change.

- 241-photo folder: 241 table rows, **241 markers on the map**, popup opens and is filled via the channel (8.6 KB incl. thumbnail)
